- **データ保持**: 原則ローカル（外部送信なし）

## 1. 背景と独自性

### 1.1 既存ツールの調査結果

家庭向けの在庫管理アプリは数多く存在する（在庫ノート、うちメモ、買いドキ+、monoca、zaico 等）。これらを調査した結果、共通する特徴は以下のとおり。

- ほぼすべてが **手動カウント方式**（使ったら減らす / 補充したら増やす）を前提とする
- 「消費ペースの可視化」機能はあっても、それは**記録のグラフ表示にとどまる**
- 在庫数の手入力が必要なため、**継続率が低い**（多くのレビューで三日坊主が言及される）

GitHub上の購入予測系プロジェクト（`predict-next-purchase` 等）は、小売の大規模顧客データを対象とした機械学習デモであり、個人が数品目をローカルで扱う本ツールとは設計思想・規模ともに異なる。

### 1.2 本ツールの独自ポイント

| 観点 | 一般的な在庫管理アプリ | 本ツール |
|---|---|---|
| 在庫把握 | ユーザーが数えて入力 | **数えない**。購入記録のみ |
| 予測 | なし／単純なグラフ | 購入間隔からの消費速度推定 |
| 通知 | 閾値到達時 | **枯渇日 − 買い物リードタイム**で先回り |
| データ | クラウド共有前提が多い | **ローカル完結**を既定 |

「在庫を数えさせない × 購入記録だけで予測 × ローカル完結」という組み合わせに新規性があり、既存OSSの焼き直しではない。

## 2. 解決する課題

定期的に消費するが管理対象として意識されにくい消耗品（洗剤、コンタクトレンズ、ペットフード、常備薬、コーヒー豆など）は、次のどちらかに転びやすい。

- **切らす**: 気づいたらなくなっていて、すぐ手に入らず困る
- **買いすぎる**: 不安でまとめ買いし、死蔵・期限切れになる

根本原因は「在庫を正確に把握し続けることのコストが高い」こと。本ツールはその把握作業自体を不要にする。

## 3. スコープ

### 3.1 本ツールがやること

- 品目の初回登録（最小限の属性）
- 購入（または開封）のワンタップ記録
- 購入間隔からの消費速度・枯渇予測日の自動算出
- 枯渇前の先回り通知
- 通知からの買い物リスト生成と、購入記録への自動反映

### 3.2 本ツールがやらないこと（明示的非スコープ）

- 在庫数のリアルタイム正確管理（思想的に持たない）
- 家族・複数人でのリアルタイム共有（v1では非対象）
- 価格比較・ネット注文連携（非対象）
- レシートOCR・購入メール自動取り込み（将来拡張のフックのみ用意）

## 4. 想定ユーザーと利用シーン

| ユーザー像 | 困りごと | 本ツールでどうなるか |
|---|---|---|
| 一人暮らし会社員 | 平日に切らすと買いに行けない | 買い物予定日より前に枯渇しそうなら早めに通知 |

| ペット飼育者 | フードの大袋がいつ尽きるか不明 | 開封日と容量から枯渇日を推定 |
| 持病のある人 | 常備薬を切らすと受診が必要 | 安全在庫を割る前に重め通知 |

## 5. 用語定義

| 用語 | 定義 |
|---|---|
| 品目 (Item) | 管理対象の消耗品。1種類につき1レコード |
| 購入イベント (Purchase) | ある品目を購入（または開封）した記録。記録の最小単位 |

| リードタイム (lead_time) | ユーザーが次に買い物に行けるまでの想定日数 |
| 安全マージン (safety_margin) | 予測のズレに備える日数の余裕 |
| 通知日 (notify_date) | `枯渇予測日 − リードタイム − 安全マージン` |

## 6. 機能要件

各要件にはID（`FR-x`）を付し、テスト・追跡に用いる。

### FR-1 品目登録
- FR-1.1 ユーザーは品目を登録できる。必須は名称のみ。
- FR-1.2 任意属性: 標準パッケージ量、単価、季節フラグ、初期消費ペースのラフ申告（例: 週1回程度）。
- FR-1.3 初期消費ペースは予測の事前分布として用いる（[7章](#7-消費予測アルゴリズム)）。

### FR-2 購入記録
- FR-2.1 ユーザーは品目をタップするだけで「今、購入した」を記録できる。
- FR-2.2 数量・日時の入力は任意。未指定時は数量=1、日時=現在時刻。
- FR-2.3 過去日付での後追い記録も可能（記録漏れの補正）。
- FR-2.4 直近の記録を取り消せる（誤タップ対策）。

### FR-3 消費予測
- FR-3.1 購入イベントが2件以上ある品目について消費速度を推定する。
- FR-3.2 1件以下の場合はFR-1.3の事前分布のみで暫定推定する。
- FR-3.3 枯渇予測日と、その不確実性（幅）を算出する。
- FR-3.4 まとめ買い等の異常間隔に頑健であること（中央値ベース）。

### FR-4 先回り通知
- FR-4.1 `notify_date` を品目ごとに算出する。
- FR-4.2 当日が `notify_date` 以降の品目を「そろそろリスト」に載せる。
- FR-4.3 通知は1日1回のバッチ。複数品目は1通にまとめる。
- FR-4.4 ユーザーの買い物曜日を学習し、その直前に通知を寄せる（任意機能）。

### FR-5 買い物リスト
- FR-5.1 通知から「そろそろリスト」をワンタップで開ける。
- FR-5.2 リスト項目にチェックすると、その品目の購入記録が自動生成される（FR-2と一体）。
- FR-5.3 これにより記録のための追加作業が発生しない。

### FR-6 設定
- FR-6.1 リードタイム（既定: 3日）、安全マージン（既定: 2日）、通知時刻を変更できる。
- FR-6.2 全データのエクスポート／インポート（JSON）。
- FR-6.3 全データの削除。

## 7. 消費予測アルゴリズム

### 7.1 設計原則

- 個人の数品目・少データが前提。**重い機械学習は使わない**。
- 解釈可能性を最優先（なぜその予測かをユーザーに説明できること）。
- 少データ時に破綻せず、データが増えるほど実測へ寄る。

### 7.2 推定ロジック

購入イベントの**時刻列**を入力とする。品目 *i* の購入日時を
`t_1 < t_2 < ... < t_n` とする。

#### Step 1: 購入間隔の算出
```
intervals = [t_2 - t_1, t_3 - t_2, ..., t_n - t_{n-1}]   # 単位: 日
```

#### Step 2: 代表間隔の推定（外れ値に頑健）
- `n >= 4` のとき: `interval_hat = median(intervals)`
- `2 <= n <= 3` のとき: `median` と事前分布申告を重み付き平均
- `n <= 1` のとき: 事前分布申告のみ（`prior_interval`）

事前分布申告 `prior_interval` は FR-1.3 のラフ申告（例: 「週1回」→ 7日）から得る。

重み付けの考え方（ベイズ更新の単純版）:
```
w_data  = n / (n + k)        # k は事前の強さ（既定 k = 2）
w_prior = 1 - w_data
interval_hat = w_data * median(intervals) + w_prior * prior_interval
```
データが増えるほど `w_data → 1` となり、実測に収束する。

#### Step 3: 消費速度と枯渇予測
1回の購入で `package_qty`（標準パッケージ量、既定1）を補充するとみなす。

```
consumption_rate = package_qty / interval_hat            # 量/日
last_purchase    = t_n
expected_runout  = last_purchase + interval_hat          # 次に尽きる推定日
```

#### Step 4: 不確実性の幅
```
spread = IQR(intervals)  またはデータ不足時は interval_hat * 0.3
depletion_low  = last_purchase + (interval_hat - spread/2)
depletion_high = last_purchase + (interval_hat + spread/2)
```
UIでは「約○日後（早ければ△日後）」のように幅を提示する。

#### Step 5: 通知日
```
notify_date = expected_runout - lead_time - safety_margin
```

### 7.3 季節性（任意・v2）
季節フラグ付き品目は、月別の購入頻度補正係数を掛ける。MVPでは無効でよい。

### 7.4 擬似コード

```python
from statistics import median
from datetime import timedelta

def estimate(purchases, item, settings, prior_k=2):
    """purchases: 昇順の datetime のリスト"""
    n = len(purchases)
    pkg = item.package_qty or 1.0
    prior_interval = item.prior_interval_days  # 例: 7.0

    if n <= 1:
        interval_hat = prior_interval
        spread = prior_interval * 0.3
    else:
        intervals = [
            (purchases[i] - purchases[i-1]).total_seconds() / 86400.0
            for i in range(1, n)
        ]
        med = median(intervals)
        if n >= 4:
            interval_hat = med
            spread = _iqr(intervals)
        else:
            w_data = n / (n + prior_k)
            interval_hat = w_data * med + (1 - w_data) * prior_interval
            spread = interval_hat * 0.3

    last = purchases[-1]
    expected_runout = last + timedelta(days=interval_hat)
    notify_date = expected_runout - timedelta(
        days=settings.lead_time + settings.safety_margin
    )
    return {
        "consumption_rate": pkg / interval_hat,
        "expected_runout": expected_runout,
        "depletion_low":  last + timedelta(days=interval_hat - spread/2),
        "depletion_high": last + timedelta(days=interval_hat + spread/2),
        "notify_date": notify_date,
    }
```

## 8. データモデル

SQLite を既定とする。すべてローカル。

### 8.1 テーブル定義

#### `items`
| カラム | 型 | 制約 | 説明 |
|---|---|---|---|
| id | INTEGER | PK | 品目ID |
| name | TEXT | NOT NULL | 名称 |
| package_qty | REAL | DEFAULT 1.0 | 1購入あたり補充量 |
| unit_price | REAL | NULL | 単価（任意） |
| prior_interval_days | REAL | NULL | 初期消費ペース申告（日） |
| is_seasonal | INTEGER | DEFAULT 0 | 季節品フラグ |
| created_at | TEXT | NOT NULL | 作成日時(ISO8601) |
| archived | INTEGER | DEFAULT 0 | 論理削除 |

#### `purchases`
| カラム | 型 | 制約 | 説明 |
|---|---|---|---|
| id | INTEGER | PK | 購入ID |
| item_id | INTEGER | FK→items.id | 対象品目 |
| purchased_at | TEXT | NOT NULL | 購入日時(ISO8601) |
| quantity | REAL | DEFAULT 1.0 | 数量 |
| source | TEXT | DEFAULT 'manual' | 記録元(manual/list/import) |

#### `settings`（単一行）
| カラム | 型 | 既定 | 説明 |
|---|---|---|---|
| lead_time_days | INTEGER | 3 | 買い物リードタイム |
| safety_margin_days | INTEGER | 2 | 安全マージン |
| notify_time | TEXT | '08:00' | 通知時刻 |
| shopping_weekday | INTEGER | NULL | 学習した買い物曜日(0=月) |

#### `estimates`（キャッシュ。再生成可能）
| カラム | 型 | 説明 |
|---|---|---|
| item_id | INTEGER | FK→items.id |
| consumption_rate | REAL | 量/日 |
| expected_runout | TEXT | 枯渇予測日 |
| depletion_low | TEXT | 早い側 |
| depletion_high | TEXT | 遅い側 |
| notify_date | TEXT | 通知日 |
| updated_at | TEXT | 算出日時 |

> **設計上の重要点**: `purchases` だけが一次データ。`estimates` はいつでも全消去・再計算できる派生データであり、バックアップ対象は `items` / `purchases` / `settings` のみで十分。

### 8.2 ER概略

```
items 1 ──< purchases
items 1 ── 1 estimates   (派生・キャッシュ)
settings (singleton)
```

## 9. アーキテクチャ

### 9.1 方針

スマホ操作が目標だが、個人用OSS・Python実装という制約から、**ローカルWebアプリ方式**を推奨する。

- バックエンド: Python（FastAPI もしくは Flask）。ローカルで起動。
- フロントエンド: スマホブラウザで開く軽量HTML/JS。PWA化してホーム画面追加・オフライン動作・ローカル通知に対応。
- DB: SQLite ファイル1個。
- スケジューラ: 1日1回の予測再計算＋通知判定バッチ。

この構成なら追加サーバ不要・依存最小で、Pythonのみで完結し、スマホからは「ホーム画面のアイコン」として日常使いできる。

### 9.2 構成図

```
┌─────────────── スマホ ───────────────┐
│  PWA (HTML/JS)                        │
│   - 品目一覧 / ワンタップ記録          │
│   - そろそろリスト                     │
│   - ローカル通知 (Notification API +   │
│     Service Worker)                   │
└───────────────┬───────────────────────┘
                │ HTTP (localhost / LAN)
┌───────────────▼───────────────────────┐
│  Python バックエンド (FastAPI/Flask)   │
│   - REST API (10章)                    │
│   - 予測エンジン (7章)                  │
│   - 日次バッチ (予測再計算・通知判定)   │
└───────────────┬───────────────────────┘
                │
        ┌───────▼────────┐
        │ SQLite (1ファイル)│
        └────────────────┘
```

### 9.3 動作モード

- **ローカル単体**: PC/サーバ上でバックエンド常駐、同一LANのスマホからアクセス。
- **将来**: 端末内SQLite + 完全オフラインPWA化（バックエンドをWASM/ローカル化）も検討余地（[18章](#18-将来拡張)）。

## 11. 画面・操作フロー

### 11.1 画面一覧

| 画面 | 目的 | 主要素 |
|---|---|---|
| ホーム（品目一覧） | 状態の一覧把握と記録 | 品目カード（状態色）、各カードに「買った」ボタン |
| そろそろリスト | 買い物時の確認 | チェックボックス付きリスト、チェックで記録 |

| 設定 | 個人化 | リードタイム・マージン・通知時刻・データ入出力 |

### 11.2 主要フロー

**初回セットアップ**
```
起動 → 品目を3〜10個登録（名称だけでも可）→ 完了
```

**日常（記録）**
```
ホーム → 対象品目の「買った」をタップ → 完了（即記録、ダイアログなし）
```

**買い物（リスト活用）**
```
通知タップ → そろそろリスト → 買ったものにチェック
   → チェックした品目の購入記録が自動生成 → 予測更新
```

### 11.3 状態の色分け

| status | 意味 | 表示 |
|---|---|---|
| ok | 当面余裕 | 通常 |
| soon | notify_date到達 | 強調（要補充候補） |
| overdue | 枯渇予測日超過 | 警告 |

### 11.4 UI原則

- 記録は**1タップ・確認ダイアログなし**（取消で担保）。
- 数量入力などは常に任意、既定値で素通りできる。
- 文字情報は最小限。状態は色とアイコンで即判別できること。

## 12. 通知設計

通知過多は即アンインストールにつながるため、抑制を最優先する。

- **頻度**: 1日1回バッチのみ。リアルタイム通知はしない。
- **集約**: 対象品目が複数でも通知は1通（「3点がそろそろです」）。
- **タイミング**: 設定の通知時刻に判定。買い物曜日学習が有効なら、その前日に寄せる。
- **無通知日**: 対象品目ゼロの日は通知しない（沈黙を守る）。
- **実装**: PWAのService Worker + Notification API によるローカル通知。サーバプッシュは不要。

### 12.1 買い物曜日の学習（任意・FR-4.4）

`purchases.purchased_at` の曜日分布を集計し、最頻曜日を `settings.shopping_weekday` に保存。通知日がその曜日の前日に来るよう ±1〜2日の範囲で寄せる。データが少ない初期は無効。

## 16. テスト方針

予測ロジックが本ツールの心臓であり、ここを重点的に検証する。

- **単体テスト（最優先）**: `forecast.py`
  - 購入0/1件 → 事前分布のみで破綻しないこと
  - 等間隔データ → 間隔がそのまま推定されること
  - まとめ買い（極端に短い間隔が混入）→ 中央値で吸収されること
  - データ増加に伴い事前分布から実測へ収束すること
- **APIテスト**: 記録→予測→そろそろリスト→チェックで記録自動生成、の一連
- **回帰テスト**: 既知の購入列に対する `notify_date` をスナップショット化
- **手動シナリオ**: 数週間の擬似データを流し込み、通知タイミングの妥当性を目視確認

## 17. OSS公開にあたっての注意

GitHub公開を前提とするため、盗作・ライセンス問題を避ける指針を明記する。

1. **独自実装であることの担保**: 予測ロジック（7章）は公知の統計手法（中央値、IQR、単純なベイズ的重み付け）の組み合わせであり、特定の既存OSSのコードを流用しない。設計・コードはゼロから書く。
2. **先行事例への敬意**: READMEに「家庭向け在庫管理アプリは多数存在するが、本ツールは『在庫を数えない・購入記録のみ・ローカル完結』という点で差別化している」と明記し、誇大な独自性主張をしない。
3. **第三者コード混入時の出典明記**: ライブラリ利用にとどめ、コード片を借用する場合は必ず出典とライセンスを `NOTICE` / コメントに記載。
4. **ライセンス選定**: 個人OSSとして広く使われる MIT または Apache-2.0 を推奨（特許条項を重視するなら Apache-2.0）。`LICENSE` を必ず同梱。
5. **依存ライブラリのライセンス確認**: 採用前に各依存のライセンス互換性を確認し、`THIRD_PARTY_LICENSES` にまとめる。
6. **個人データを含めない**: サンプルデータ・スクリーンショットに実在の購入履歴や個人情報を含めない。`.gitignore` でローカルDB（`*.sqlite`）を除外。
7. **健康関連の免責**: 常備薬等を扱い得るため、README/アプリ内に「本ツールの予測は補助であり、医療・在庫の正確性を保証しない」旨の免責を記載。

## 付録A: 設計上の不変原則（実装中に迷ったらここへ戻る）
